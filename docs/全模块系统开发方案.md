# 玄学五术平台 · 全模块系统开发方案

> 版本：v1.0
> 定位：以现有 `destiny`（子平八字）系统为地基，插件化扩展为覆盖「东方传统术数 / 西方及印度星象 / 符号与媒介占卜 / 人体数理与现代系统」四大模块的综合性玄学平台。
> 性质声明：本产品全线定位为**传统文化与娱乐参考**，不构成医疗、投资、法律、心理诊断等任何专业建议。

---

## 0. 文档定位与阅读方式

本方案不是"从零设计"，而是在已验证可跑通的 `destiny` 八字系统之上做**架构升级**。阅读顺序建议：

1. 第一、二章：理解总体战略与架构升级方案（所有新模块都要遵守的统一契约）。
2. 第三～六章：四大模块逐一拆解，每个术数系统给出「算法要点 / 数据结构 / 工作量估算 / 优先级 / 风险」。
3. 第七章：把所有模块汇总成一张可执行的排期表。
4. 第八～十三章：落地所需的数据模型、API、前端、计费、合规、技术选型细节。

## 一、总体战略

### 1.1 现状判断

`destiny` 当前是一个**打磨得比较完整的单一术数系统**（子平八字）：规则引擎纯函数排盘 + RAG 知识库 + LLM 解读 + 账户计费闭环，工程质量已达到"可复制"的程度。这套组合（**引擎负责准，AI 负责讲**）是本次扩展的核心方法论，将原样复用到全部新模块。

### 1.2 演进原则

- **不推倒重来**：现有 `bazi-engine` / `charts` / `reports` / `ai` 模块保持不变，作为"参照实现"，新模块照此模式复制。
- **插件化扩展**：每个术数系统是一个独立的引擎包（monorepo package），通过统一接口注册进系统，互不耦合。
- **分层复用**：账户体系、计费体系、RAG 检索框架、Prompt 编排框架、前端布局组件全部复用，只有"排盘/起卦算法"和"知识库内容"是每个模块独有的。
- **按性价比排期**：不按术数系统的"传统地位"排优先级，按**开发工作量 / 技术风险 / 用户价值**排期（详见第七章），塔罗、生命灵数这类低成本高体验的模块反而应该先做。

### 1.3 目标形态

```
玄学五术平台
├── 模块一：东方传统术数（子平八字 ✅ → 紫微斗数 → 六爻 → 梅花/小六壬 → 奇门 → 风水 → 面相手相）
├── 模块二：西方及印度星象（西方占星 → 印度占星 → 中国古占星）
├── 模块三：符号与媒介占卜（塔罗 → 卢恩 → 占星骰 → 神谕卡框架 → 自然媒介）
└── 模块四：人体数理与现代系统（生命灵数 → 梦境解析 → 测字 → 笔迹学）
```

每个术数系统落地时都对应功能树要求的三个二级功能：
- **工具库**：排盘/起卦计算引擎 + API + 交互 UI（本方案的核心内容）。
- **使用教程**：轻量 CMS 内容（新增 `Content` 表，见第八章）。
- **案例解析**：同样走 `Content` 表，可与 RAG 知识库联动做"真实案例 + AI 复盘"。

这是本方案最关键的一章：只要新模块遵守这里定义的接口，就能直接接入现有的账户、计费、AI 解读、前端布局体系，不需要重新做一套。

### 2.3 统一引擎接口（TypeScript 契约）

每个新术数系统都在 `packages/` 下新建一个包，导出符合以下接口的实现（对齐 PRD 中"深度分析"部分提出的 `FortuneSystem` 构想，这里给出可直接编码的完整版本）：

```typescript
// packages/divination-core/src/types.ts
// 全部术数引擎必须实现的统一契约

/** 术数系统标识，与 Chart.systemType 字段一致 */
export type SystemType =
  | 'bazi'        // 子平八字（已实现）
  | 'ziwei'       // 紫微斗数
  | 'liuyao'       // 六爻
  | 'qimen'        // 奇门遁甲
  | 'meihua'       // 梅花易数
  | 'xiaoliuren'   // 小六壬
  | 'western_astrology'   // 西方占星
  | 'vedic_astrology'     // 印度占星
  | 'tarot'        // 塔罗
  | 'rune'         // 卢恩符文
  | 'numerology'   // 生命灵数
  | 'dream'        // 梦境解析
  | 'ceyi'         // 测字
  | 'palm_face';   // 面相手相

/** 输入分两类：出生信息类 / 起卦事件类 */
export interface BirthBasedInput {
  kind: 'birth';
  calendar: 'solar' | 'lunar';
  year: number; month: number; day: number;
  hour: number | null; minute: number | null;
  gender: 'male' | 'female';
  longitude: number; latitude: number;
  useTrueSolarTime: boolean;
}

export interface DivinationEventInput {
  kind: 'event';
  /** 起卦时间（六爻/奇门/梅花均需要） */
  eventDatetime: string; // ISO
  /** 起卦方式相关参数：摇卦数字、随机数、用户输入的问题等 */
  method: string;         // 'coin' | 'time' | 'number' | 'random' ...
  params: Record<string, unknown>;
  question?: string;      // 占问事项（一事一测类必填）
}

export type EngineInput = BirthBasedInput | DivinationEventInput;

/** 引擎输出：结构化结果 + 供 AI 解读用的"事实块"文本 */
export interface EngineOutput<TChart = unknown> {
  systemType: SystemType;
  engineVersion: string;
  /** 结构化数据（每个引擎自定义具体形状，前端按 systemType 分支渲染） */
  chart: TChart;
  /** 已格式化好的、可直接注入 LLM Prompt 的事实描述（对齐现有 formatChartFacts 模式） */
  factsText: string;
  /** 供 RAG 检索用的特征标签（对齐现有 extractFeatureTags 模式） */
  featureTags: string[];
}

/** 统一引擎接口 */
export interface DivinationEngine<TChart = unknown> {
  readonly systemType: SystemType;
  readonly engineVersion: string;
  /** 校验输入合法性，失败抛出业务异常 */
  validate(input: EngineInput): void;
  /** 纯函数计算，无 I/O，确定性可复现 */
  calculate(input: EngineInput): EngineOutput<TChart>;
}
```

### 2.4 引擎注册表

```typescript
// apps/api/src/modules/divination/engine-registry.service.ts
@Injectable()
export class EngineRegistryService {
  private readonly engines = new Map<SystemType, DivinationEngine>();

  register(engine: DivinationEngine): void {
    this.engines.set(engine.systemType, engine);
  }

  get(systemType: SystemType): DivinationEngine {
    const engine = this.engines.get(systemType);
    if (!engine) throw new NotFoundException(`未注册的术数系统: ${systemType}`);
    return engine;
  }

  listAvailable(): SystemType[] {
    return [...this.engines.keys()];
  }
}
```

新模块接入只需三步：
1. 在 `packages/` 下实现 `DivinationEngine` 接口（复用 `bazi-engine` 的目录结构：`core/`、`constants/`、`types/`）。
2. 在 `AiModule` 下新增对应的 `knowledge.data.ts`（RAG 语料）与 `prompt.builder`（可复用现有 `SYSTEM_CONSTRAINTS` / `STRUCTURED_OUTPUT_GUIDE` 常量，只替换排盘事实块的格式化函数）。
3. 在 `DivinationModule` 里注册引擎，前端新增一个 `systemType` 分支的表单与结果渲染组件。

### 2.5 现有模块的最小改动清单

| 模块 | 改动 | 兼容性 |
|---|---|---|
| `Chart` 数据表 | 新增 `systemType` 字段（默认值 `'bazi'`），`chartJson` 结构不变仍为 `Json` | 向后兼容，现有八字数据无需迁移 |
| `ChartsController/Service` | 抽象出 `DivinationController/Service`，八字相关方法保留作为 `systemType='bazi'` 的具体实现 | 现有 `/charts/*` 路由保留，新增 `/divination/:systemType/*` |
| `ReportsService` | `generateDimension` 等方法从"硬编码引用 `formatChartFacts`"改为"调用 `engine.factsText`" | 八字维度报告逻辑不变 |
| `RagService` | `retrieve()` 增加 `systemType` 参数，按类型过滤知识库 | 默认 `systemType='bazi'` 保持现状行为 |
| `KnowledgeChunk` 表 | 新增 `systemType` 字段 | 现状数据补默认值即可 |
| 前端 `chart/[id]/page.tsx` | 拆分为"八字详情"组件 + 按 `systemType` 动态加载对应可视化组件 | 现有八字页面逻辑整体平移，不改视觉 |

## 三、模块一：东方传统术数系统

### 3.1 子平八字（✅ 已实现，v1.2.0）

现状：四柱排盘、五行旺衰、十神、大运流年、神煞（11种带出处）、格局（8种）、合冲刑害破（9种关系）、真太阳时校正、AI 七维度报告 + 通俗概览 + 问答。

**后续深化项**（非新模块，是现有模块打磨）：
| 任务 | 说明 | 工作量 |
|---|---|---|
| 命例对比库 | 用户可与历史名人/典型命例对比五行结构 | 3 人日 |
| 更多格局判定 | 目前 8 种（建禄/阳刃/食神/伤官/食神制杀/伤官配印/财官双美/从格），可扩展至 20+ | 5 人日 |
| 流月/流日 | 目前只到流年颗粒度，精细用户需要流月 | 4 人日（在 `luck.ts` 扩展） |

### 3.2 紫微斗数（新增，优先级：高）

**定位**：模块一里除八字外用户认知度最高的系统，且与八字同属"出生信息类"输入，可直接复用 `BirthBasedInput`，复用度最高。

**算法要点**：
- 安十四主星（紫微、天机、太阳、武曲、天同、廉贞、天府、太阴、贪狼、巨门、天相、天梁、七杀、破军）到十二宫。
- 安十二宫（命宫、兄弟、夫妻、子女、财帛、疾厄、迁移、交友、官禄、田宅、福德、父母）。
- 四化飞星（化禄、化权、化科、化忌，按生年干）。
- 三方四正、十二宫互动关系。
- 大限/流年（斗数的"大运"概念，十年一限，与八字大运并行但算法不同）。

**数据结构草案**：
```typescript
interface ZiweiChart {
  lifePalaceIndex: number;      // 命宫地支索引
  palaces: ZiweiPalace[];       // 12 宫
  sihua: { lu: string; quan: string; ke: string; ji: string }; // 四化对应的星
  bodyPalaceIndex: number;      // 身宫
  fiveElementBureau: string;    // 五行局（水二局/木三局...起大限用）
}
interface ZiweiPalace {
  name: string;         // 命宫/兄弟宫/...
  branch: EarthlyBranch;
  mainStars: string[];   // 落入该宫的主星
  minorStars: string[];  // 辅星（左辅右弼/文昌文曲/擎羊陀罗等）
  sihuaMarks: string[];  // 该宫内被四化标记的星
}
```

**技术风险**：紫微斗数的排盘规则（尤其安星法）流派差异大（中州派/钦天四化派等口径不同），需要在文档里明确"采用中州派通行排法"并在免责声明中注明流派。

**工作量估算**：引擎 8-10 人日（含安星表、四化表、大限流年算法）+ 测试黄金样例 3 人日 + RAG 知识库（十四主星、十二宫、四化组合，约 60-80 条）3 人日 + 前端命盘可视化（十二宫格布局，比四柱表复杂）5 人日 = **约 19-21 人日**。

### 3.3 六爻（新增，优先级：中高）

**定位**：模块一"一事一测"的入口级产品，起卦方式多样（摇卦/时间起卦/数字起卦），交互性强，适合做成"每日一测"的轻量高频功能，拉动 DAU。

**算法要点**：
- 装卦：六个爻位（自下而上）分配天干地支（纳甲）、五行、六亲。
- 世应：确定世爻、应爻位置。
- 用神：根据占问事项确定用神（测财用财爻、测官用官爻等）。
- 六神：青龙/朱雀/勾陈/螣蛇/白虎/玄武，按日干起。
- 动爻变卦：动爻的阴阳变化生成"变卦"，与本卦对照分析。
- 生克冲合：世应与用神的生克关系判定吉凶。

**数据结构草案**：
```typescript
interface LiuYaoChart {
  question: string;          // 占问事项
  method: 'coin' | 'time' | 'number' | 'manual';
  lines: LiuYaoLine[];       // 6 爻，index 0=初爻...5=上爻
  hexagramName: string;      // 本卦名（如"乾为天"）
  changedHexagramName?: string; // 变卦名（有动爻时）
  worldLineIndex: number;    // 世爻位置
  responseLineIndex: number; // 应爻位置
  usefulGod: string;         // 用神
}
interface LiuYaoLine {
  yinYang: 'yin' | 'yang';
  moving: boolean;           // 是否动爻
  najiaStem: HeavenlyStem;
  najiaBranch: EarthlyBranch;
  liuQin: string;            // 六亲：父母/兄弟/子孙/妻财/官鬼
  sixBeast: string;          // 六神
}
```

**工作量估算**：引擎（纳甲装卦表 + 六神表 + 用神判定规则）7-9 人日 + 测试样例 2 人日 + RAG 知识库（64卦卦辞、六亲六神含义，约 100 条，工作量较大因需覆盖 64 卦）5-6 人日 + 前端（摇卦动画 + 六爻图）4 人日 = **约 18-21 人日**。

### 3.4 梅花易数 / 小六壬（新增，优先级：高，性价比最优）

**定位**：模块一里**算法最简单、最适合作为"轻量占卜"引流产品**的两个系统。梅花易数按数字/时间起卦，小六壬按时辰掌诀速断，均无需复杂排盘引擎，几小时可完成核心算法。

**算法要点（梅花易数）**：
- 起卦法：时间起卦（年月日时数相加取余）、数字起卦（用户输入两个数字）、任意数起卦。
- 上卦/下卦：数字对应八卦（乾1兑2离3震4巽5坎6艮7坤8）。
- 动爻：总数除6取余定动爻。
- 体用：上下卦分体卦用卦，用卦生克体卦定吉凶。
- 互卦：抽取二三四爻、三四五爻组新卦，看事情发展过程。

**算法要点（小六壬）**：
- 六宫掌诀：大安、留连、速喜、赤口、小吉、空亡。
- 起法：以农历月日时三数按掌诀轮转，比梅花易数更简化，是最快的"随手一测"工具。

**工作量估算（两者合并）**：引擎（八卦数字映射 + 体用生克 + 小六壬六宫表）4-5 人日 + RAG 知识库（八卦卦象 64 条 + 六宫吉凶 6 条）3 人日 + 前端（起卦交互，输入数字/时间即出结果）3 人日 = **约 10-11 人日**。ROI 全模块最高，建议第一批开发。

### 3.5 奇门遁甲 / 大六壬 / 太乙神数（新增，优先级：低，复杂度最高）

**定位**：传统术数中公认**最复杂**的排盘系统，涉及三奇六仪、九宫飘泊、时空双重坐标，且流派分化严重（转盘/飞盘奇门口径不同）。建议排在所有东方术数模块的**最后**，且需要单独请命理顾问校验排盘准确性。

**工作量估算**：引擎 15-20 人日 + 黄金测试集校验（必须找专业命理师核对，纯工程测试无法保证准确） 5 人日+ RAG 知识库 8-10 人日 + 前端（九宫格可视化）6 人日 = **约 34-41 人日**，且存在"排盘规则本身在业内没有统一共识"的项目风险，实施前需先做流派选型决策。

### 3.6 铁板神数 / 七政四余（新增，优先级：最低，不建议 v1-v3 做）

这两个系统在现存资料的完整度、数字化难度上都远超其他系统（铁板神数需要海量"条文"检索库，本质是一个命理版的专家系统/大规模文本检索，而非纯计算）。建议**长期规划**里保留位置，但不纳入前三个开发阶段。

### 3.7 面相 / 手相（新增，优先级：中，依赖图像识别）

**定位**：唯一需要"计算机视觉"能力的东方术数模块，技术栈与其他模块差异最大（其他都是规则引擎，这个需要图像模型）。

**技术方案**：
- 用户上传照片 → 调用人脸关键点检测（可用开源模型如 MediaPipe Face Mesh，或直接让多模态 LLM（如 GPT-4o / Qwen-VL）做图像描述）→ 把面部特征（五官比例、掌纹走势）转成结构化描述 → 走现有 RAG + LLM 解读管线。
- **不建议自建训练模型**，直接用多模态 LLM 做图像特征提取 + Prompt 约束输出，成本和周期都可控。

**合规风险（重要，需重点提示）**：涉及**人脸生物特征数据**，属于敏感个人信息，法律要求更严格（参照《个人信息保护法》对生物识别信息的特殊保护）：
- 图片必须加密存储或**不落库、用完即焚**（推荐后者，处理完立即删除原图，只保留 AI 生成的文字描述）。
- 必须在采集前单独取得用户"生物识别信息处理"的明示同意（不能和其他条款合并勾选）。
- 需明确告知留存期限、使用目的，且不用于人脸识别/身份核验等目的。

**工作量估算**：图像接入与 Prompt 设计 5-7 人日 + RAG 知识库（面相十二宫、掌纹三大线，约 40 条）4 人日 + 前端（拍照/上传 + 结果标注） 5 人日 + 合规流程（独立同意书、数据处理协议） 2 人日 = **约 16-18 人日**。

### 3.8 风水堪舆（新增，优先级：中低）

**定位**：与其他模块不同，风水本质是"空间分析"，输入是户型图/朝向而非出生信息，产品形态更接近"上传户型图 + 标注朝向 → 给布局建议"。

**技术方案**：
- 罗盘方位计算：纯数学（房屋朝向角度 → 二十四山），可复用 `bazi-engine` 里已有的干支/五行常量。
- 峦头理气分析：需要户型图输入，v1 可简化为"用户手动标注房间朝向和用途"，不做图像自动识别（图像识别户型图是独立的高难度 CV 任务，不建议在此阶段投入）。
- 家居布局建议：走 RAG + LLM，输入结构化的"房间朝向 + 用途 + 居住者八字喜用神"，输出布局建议文本。

**亮点**：可与八字模块联动（"结合你的喜用神五行，卧室建议摆放方位"），是**模块间协同**的一个好范例。

**工作量估算**：引擎（罗盘方位 + 二十四山计算）5 人日 + RAG 知识库（峦头理气规则，约 50 条）5 人日 + 前端（户型标注交互，比其他模块复杂）8 人日 = **约 18 人日**。

## 四、模块二：西方及印度星象系统

### 4.1 西方占星（新增，优先级：中，技术门槛最高的"正统"系统）

**定位**：全球用户认知度和搜索量最高的占卜系统之一（欧美市场），但**精确星盘计算依赖天文历表**，不是规则查表能搞定的，是本方案里对"计算精度"要求最高的模块。

**技术方案（关键决策点）**：
- **强烈建议直接使用现成天文计算库**，而不是自己实现行星轨道计算：
  - Swiss Ephemeris（瑞士星历表，`swisseph` 的 Node.js 绑定或 WASM 版本）是业界事实标准，精度可达角分级别，NASA JPL 数据支撑。
  - 若走 WASM/原生绑定在 Node 服务器环境有兼容性风险，需提前用 Docker 环境验证可编译运行。
- 星盘计算流程：出生时间+经纬度 → Swiss Ephemeris 算出十大行星（日月水金火木土天海冥）+ 月交点(Rahu/Ketu 的西方对应)的黄道经度 → 宫位系统计算（常用 Placidus 制）→ 相位计算（行星间角度差，合相/刑相/拱相/冲相/六合相）。
- 流年推运：Transit（行星当前位置与本命盘比对）与 Progression（次限法）两种技法，v1 建议只做 Transit（计算逻辑更简单，用户也更容易理解"现在木星走到你哪个宫位"）。

**数据结构草案**：
```typescript
interface WesternAstrologyChart {
  planets: PlanetPosition[];  // 10 大行星 + 月交点
  houses: HouseCusp[];        // 12 宫头黄道经度（Placidus制）
  aspects: Aspect[];          // 相位列表
  ascendant: number;          // 上升点黄道经度
  midheaven: number;          // 天顶
}
interface PlanetPosition {
  planet: string;    // Sun/Moon/Mercury/.../Rahu/Ketu
  sign: string;      // 所在星座
  degree: number;    // 星座内度数
  house: number;     // 落入几宫
  retrograde: boolean; // 是否逆行
}
interface Aspect {
  planetA: string; planetB: string;
  type: 'conjunction' | 'sextile' | 'square' | 'trine' | 'opposition';
  angle: number;
  orb: number;       // 容许度误差
}
```

**工作量估算**：Swiss Ephemeris 集成与验证 4-6 人日（含跨平台兼容性排查）+ 宫位/相位算法 5 人日 + 黄金测试集（与专业占星软件如 Astro.com 结果对照校验）3 人日 + RAG 知识库（12 星座×10 行星组合、12 宫位、5 种主要相位，量级较大，约 150-200 条）8-10 人日 + 前端（圆形星盘可视化，技术难度高于四柱表/十二宫格）8-10 人日 = **约 28-35 人日**。这是除奇门遁甲外工作量最大的单一模块，主要成本在"星盘 SVG 可视化"和"知识库覆盖度"。

### 4.2 印度占星（吠陀）（新增，优先级：中低，依赖西方占星基础设施）

**定位**：与西方占星共享底层天文计算（同样需要 Swiss Ephemeris），但采用恒星黄道（Sidereal）而非回归黄道（Tropical），核心差异在"精确度修正值（Ayanamsa）"和技法体系。

**技术方案**：
- 复用西方占星模块的 Swiss Ephemeris 集成，切换 `SIDM_LAHIRI`（最常用的 Ayanamsa 标准）计算模式。
- Nakshatra（27 星宿）：月亮所在的精确星宿，是吠陀占星的核心，比西方的"月亮星座"颗粒度更细。
- 业力行星 Rahu/Ketu：即月交点，西方占星里已计算，此处引用同一数据，只是解读体系不同。
- Dasha 大运系统：最复杂的部分，Vimshottari Dasha（120 年周期，按月亮所在星宿分配各行星"当值期"），需要专门实现。

**工作量估算**（在西方占星模块已完成的前提下）：Ayanamsa 切换 + Nakshatra 表 3 人日 + Vimshottari Dasha 算法 5-6 人日 + RAG 知识库（27 星宿+9 大行星 Dasha 组合，约 100 条）6 人日 + 前端复用西方占星星盘组件，仅调整宫位/星宿标注 3 人日 = **约 17-20 人日**。**强烈建议在西方占星模块完成之后才做**，独立开发西方占星基础设施的成本无法摊销。

### 4.3 中国古占星（果老星宗）（新增，优先级：最低）

果老星宗是中西合璧的历史产物（融合了黄道十二宫与中国二十八宿），现存资料稀少，考据成本高，且用户认知度在四个模块里最低。**建议排在整个路线图的末尾，作为"内容完整性"补充而非核心功能**，工作量暂不做详细估算，视前面模块完成情况再评估。

## 五、模块三：符号与媒介占卜系统

这个模块的共同特点：**都不依赖出生信息**，输入是"当下的随机事件"（抽牌/掷骰/摇符文），计算逻辑通常是"加权随机数生成 + 结果查表解读"，是**全平台技术难度最低、但内容量（牌义库）要求高**的模块，适合作为高频轻量互动功能，对新用户转化和日活拉动效果最好。

### 5.1 塔罗牌（新增，优先级：最高，建议整个项目第一个新增模块）

**定位**：全球认知度最高的占卜工具之一，算法极简（伪随机抽牌 + 查表），核心成本在牌义内容库和牌面视觉资源，是**性价比之王**，建议作为四大模块中除八字深化外的第一个交付目标。

**技术方案**：
- 78 张牌（22 张大阿卡纳 + 56 张小阿卡纳）+ 正逆位 = 156 种基础牌义单元。
- 经典牌阵：单张牌、三张牌（过去-现在-未来）、凯尔特十字（10张，最经典的深度牌阵）。
- 抽牌算法：加密安全随机数（`crypto.randomInt`），不放回抽样，正逆位各 50% 概率。
- 解读：抽到的牌（含正逆位、牌阵位置含义）→ RAG 检索对应牌义 → LLM 组合成关联问题的整体解读。

**数据结构草案**：
```typescript
interface TarotReading {
  question: string;
  spreadType: 'single' | 'three_card' | 'celtic_cross';
  cards: TarotDraw[];
}
interface TarotDraw {
  positionName: string;   // 牌阵位置含义，如"过去"/"现在"/"潜在影响"
  cardId: string;         // 如 'major_00_fool'
  cardName: string;       // 愚者
  orientation: 'upright' | 'reversed';
}
```

**RAG 知识库设计**：78 张牌 × 正逆位 × （通用含义+爱情+事业+财运）≈ 78×2×4 = 624 个知识片段，是全平台知识库工作量最大的单项，但**牌义内容有大量公开的权威资料可参考整理**（如 Rider-Waite 体系标准牌义），整理效率高于口诀类知识（如奇门遁甲）。

**工作量估算**：引擎（抽牌算法+牌阵定义）2-3 人日 + RAG 知识库（624 条，含内容整理与审校）10-12 人日 + 前端（牌面视觉资源制作/采购 + 翻牌动画交互）8-10 人日 = **约 20-25 人日**，其中前端牌面美术资源如果采购现成的开源/商用授权牌面图集可大幅压缩工作量。

### 5.2 神谕卡 / 扑克牌占卜（新增，优先级：中，复用塔罗基础设施）

**定位**：与塔罗共享抽牌引擎（只是牌库和牌义不同），神谕卡无固定体系（品牌众多），建议 v1 只做"扑克牌占卜"（54张牌，规则统一、无版权顾虑），神谕卡留待后续按具体产品化需求（如与某个原创神谕卡品牌合作）再做。

**工作量估算（扑克牌占卜）**：复用塔罗抽牌引擎，仅新增牌义映射表 1 人日 + RAG 知识库（54 张×基础含义，约 60 条）3 人日 + 前端复用塔罗翻牌组件 1-2 人日 = **约 5-6 人日**，极低成本的内容延伸。

### 5.3 卢恩符文（新增，优先级：中）

**技术方案**：24 个字母（老弗萨克文字母表）+ 1 个空白符（部分体系包含），抽取方式类似塔罗（单符文/三符文阵），解读风格偏"直觉指引"而非具体预测。

**工作量估算**：引擎复用塔罗抽取逻辑改造 1-2 人日 + RAG 知识库（25 符文×正逆位×基础含义，约 50 条）4 人日 + 前端（符文图形绘制，SVG 几何图案，无需美术摄影资源）3-4 人日 = **约 9-11 人日**。

### 5.4 占星星骰（新增，优先级：低）

**技术方案**：三颗骰子分别代表"行星/星座/宫位"，掷骰后组合三个随机结果生成一句解读（如"金星 + 天秤座 + 第七宫 = 关注伴侣关系中的平衡"）。本质是行星×星座×宫位的组合查表（10×12×12=1440 种组合），可用"行星含义+星座含义+宫位含义"三段式拼接生成，不需要真的写 1440 条独立文案。

**工作量估算**：引擎（掷骰 + 组合拼接逻辑）2 人日 + RAG 知识库（10 行星+12星座+12宫位的独立含义，约 34 条，比 1440 组合省力得多）3 人日 + 前端（3D 骰子动画可选，或简化为卡片翻转）3-5 人日 = **约 8-10 人日**。

### 5.5 自然物质媒介占卜（茶叶渣 / 咖啡渣 / 水晶球 / 火占蜡占）（新增，优先级：最低）

**定位**：这类占卜依赖"图案识别"（如咖啡渣形成的图案像什么）,若要认真做需要图像识别能力（类似面相模块），若简化则容易沦为"随机文案生成器"缺乏可信度。**建议不作为独立工具开发**，而是作为水晶球/塔罗模块下的"冥想引导文本"轻内容（无需交互计算，纯内容型功能，走 `Content` 表即可），不建议投入工程资源做专门引擎。

## 六、模块四：人体、数理与现代系统

### 6.1 生命灵数 Numerology（新增，优先级：最高，与塔罗并列第一批交付）

**定位**：算法比塔罗更简单（纯数字运算，无需随机数），且与出生日期直接相关，可作为**八字用户的自然延伸功能**（"顺手看看你的生命灵数"），转化路径短。

**技术方案**：
- 生命数字：出生年月日全部数字相加，反复相加至个位数（1-9），或保留 11/22/33 主数字（Master Number 规则）。
- 姓名数字（可选 v2）：需要字母转数字映射表（毕达哥拉斯或凯尔特体系），中文姓名场景下这个功能价值有限，v1 可不做。
- 各数字对应的性格/天赋/挑战解读，走标准 RAG + LLM 管线。

**数据结构草案**：
```typescript
interface NumerologyChart {
  lifePathNumber: number;      // 生命数字（1-9, 11, 22, 33）
  birthDayNumber: number;      // 出生日数字
  isMasterNumber: boolean;
  calculationSteps: string[];  // 计算过程展示（教育意义，帮用户理解怎么算出来的）
}
```

**工作量估算**：引擎（数字相加算法，含 Master Number 规则）1 人日 + RAG 知识库（1-9 + 11/22/33，共 12 条，每条可写得较详细）2-3 人日 + 前端（数字计算过程可视化 + 结果展示）2-3 人日 = **约 5-7 人日**，全平台工作量最小的模块，建议第一批交付，用于快速验证"模块化架构"是否真的能跑通。

### 6.2 测字（新增，优先级：中）

**定位**：中国传统占卜术，用户写一个字，按字形拆解（部首、笔画、结构）给出解读，是纯文本输入、无需图像识别的"轻计算"模块。

**技术方案**：
- 字形拆解：需要一个汉字拆字库（部首/笔画数据），可采用开源汉字属性数据库（如 `hanzi-writer` 的字形数据或 Unicode CJK 部首数据）。
- 五行归属：单字可按部首或笔画数映射五行（笔画尾数 1-2木、3-4火、5-6土、7-8金、9-0水，是常见简化口径之一）。
- 解读：结合拆字结果（如"钱"拆为"金"+"戈"）与占问事项，走 LLM 解读。

**工作量估算**：引擎（汉字拆字规则 + 五行映射）4-5 人日（字库整理是主要成本）+ RAG 知识库（常见部首含义、五行解读规则，约 40 条）4 人日 + 前端（手写输入/文字输入 + 拆字动画）3 人日 = **约 11-12 人日**。

### 6.3 笔迹学（新增，优先级：低，依赖图像识别）

**定位**：技术路径与面相模块相似（需要图像分析），但笔迹学的科学性争议比面相更大（西方笔迹学在心理学界普遍被视为伪科学），需要在免责声明里格外谨慎表述。

**技术方案**：用户上传手写样本图片 → 多模态 LLM 描述笔画特征（倾斜度/力度/间距/大小）→ 走 RAG+LLM 解读。同样面临图像数据的存储合规问题（虽不属于生物识别信息，但仍是用户上传的个人书写样本，建议同样"用完即焚"策略）。

**工作量估算**：图像接入 4-5 人日 + RAG 知识库（约 30 条）3 人日 + 前端 3-4 人日 = **约 10-12 人日**。

### 6.4 梦境解析（新增，优先级：中，内容型为主）

**定位**：本质是"关键词检索式内容库"（用户描述梦境关键词 → 检索对应解梦条目），比其他模块更依赖内容库的丰富度而非算法。

**技术方案**：不需要专门的"计算引擎"，`DivinationEngine` 接口里 `calculate()` 直接返回"从用户输入提取的关键词列表"，核心工作在 RAG 知识库（梦境符号词典，如"梦见蛇""梦见水"等，条目量建议 200+ 才能有基本覆盖度）。

**工作量估算**：几乎无引擎开发，关键词提取用 LLM 直接做 0.5 人日 + RAG 知识库（200+ 条，工作量集中在内容整理）10-12 人日 + 前端（描述输入 + 关键词高亮）2 人日 = **约 13-15 人日**，成本几乎全部在内容而非工程。

### 6.5 通灵板 / 扶乩记录（不建议开发）

这类内容涉及"通灵"性质表述，在内容合规上风险明显高于其他术数类目（容易被归类为封建迷信/伪科学宣传的重点审查对象，且缺乏"娱乐参考"的可辩护空间），**明确建议不纳入产品范围**。

### 6.6 科学与理性预测（气象/经济数据模型、逻辑推演引擎）（不建议作为"术数模块"开发）

这一子节的性质与前面所有模块完全不同——它是**真实的数据科学/量化分析**，不属于玄学范畴。如果确实要做，应该作为独立的"数据洞察"产品线，使用真实的气象 API / 金融数据 API，而不是套用 RAG+LLM 的命理解读模式。**不建议在本方案（玄学五术平台）的路线图中包含此项**，若用户有相关需求建议单独立项讨论。

### 阶段 M0（已完成）：子平八字地基

## 八、数据模型扩展（Prisma Schema Diff）

在现有 `schema.prisma` 基础上的**增量**改动，不影响现有八字数据。

```prisma
// ============ 改动 1：Chart 表新增 systemType 字段 ============
model Chart {
  id            String   @id @default(uuid())
  profileId     String   @map("profile_id")
  /// 新增：术数系统类型，默认 'bazi' 保持向后兼容
  systemType    String   @default("bazi") @map("system_type")
  engineVersion String   @map("engine_version")
  chartJson     Json     @map("chart_json")
  inputHash     String   @map("input_hash")
  createdAt     DateTime @default(now()) @map("created_at")

  profile  Profile       @relation(fields: [profileId], references: [id], onDelete: Cascade)
  reports  Report[]
  messages ChatMessage[]

  @@index([profileId])
  @@index([inputHash])
  @@index([systemType])   // 新增索引：便于按系统类型统计
  @@map("charts")
}

// ============ 改动 2：KnowledgeChunk 表新增 systemType 字段 ============
model KnowledgeChunk {
  id         String   @id @default(uuid())
  /// 新增：知识所属的术数系统，默认 'bazi'
  systemType String   @default("bazi") @map("system_type")
  topic      String
  tags       String[]
  content    String   @db.Text
  createdAt  DateTime @default(now()) @map("created_at")

  @@index([topic])
  @@index([systemType])
  @@map("knowledge_chunks")
}

// ============ 新增表 1：DivinationEvent（起卦类输入的记录，区别于 birth 类的 Profile）============
/// 起卦事件记录（六爻/奇门/梅花/塔罗/卢恩等"一事一测"类的输入）
/// 与 Profile（出生信息类）并列，Chart 通过 sourceType 关联其中一种
model DivinationEvent {
  id            String   @id @default(uuid())
  userId        String   @map("user_id")
  systemType    String   @map("system_type")
  /// 占问事项（塔罗/六爻等需要用户提出具体问题）
  question      String?  @db.Text
  /// 起卦方式：coin/time/number/manual/random
  method        String
  /// 起卦参数（摇卦数字、随机种子等），结构随 systemType 变化
  paramsJson    Json     @map("params_json")
  eventDatetime DateTime @map("event_datetime")
  createdAt     DateTime @default(now()) @map("created_at")

  user   User    @relation(fields: [userId], references: [id], onDelete: Cascade)
  charts Chart[] @relation("EventCharts")

  @@index([userId])
  @@index([systemType])
  @@map("divination_events")
}

// ============ 改动 3：Chart 增加可选的 eventId 关联（起卦类命盘不挂 Profile，挂 Event）============
model Chart {
  // ...上面已列字段
  profileId String?          @map("profile_id")  // 改为可选：出生信息类命盘才有
  eventId   String?          @map("event_id")    // 新增：起卦类命盘挂这里
  profile   Profile?         @relation(fields: [profileId], references: [id], onDelete: Cascade)
  event     DivinationEvent? @relation("EventCharts", fields: [eventId], references: [id], onDelete: Cascade)
  // 约束：profileId 与 eventId 二者必有一个非空（应用层校验，Prisma 不支持 XOR 约束）
}

// ============ 新增表 2：Content（教程/案例解析的轻量 CMS）============
/// 每个术数系统的「使用教程」与「案例解析」内容
model Content {
  id         String   @id @default(uuid())
  systemType String   @map("system_type")
  /// 类型：tutorial（教程）| case_study（案例解析）
  kind       String
  title      String
  /// Markdown 正文
  body       String   @db.Text
  /// 排序权重，数字越小越靠前
  sortOrder  Int      @default(0) @map("sort_order")
  published  Boolean  @default(false)
  createdAt  DateTime @default(now()) @map("created_at")
  updatedAt  DateTime @updatedAt @map("updated_at")

  @@index([systemType, kind])
  @@map("contents")
}
```

**迁移策略**：
1. `systemType` 字段用 `@default("bazi")` 保证 `prisma migrate dev` 对现有数据零改动。
2. `Chart.profileId` 改为可选（nullable）需要一次显式迁移，Prisma 会生成 `ALTER TABLE charts ALTER COLUMN profile_id DROP NOT NULL`，属于安全的向后兼容变更。
3. 新表（`DivinationEvent`、`Content`）直接 `CREATE TABLE`，无风险。

## 九、API 设计（统一入口 + 兼容现有路由）

### 9.1 新增统一入口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/divination/systems` | 返回当前已注册的术数系统列表（`EngineRegistryService.listAvailable()`），前端用于动态渲染模块导航 |
| POST | `/api/divination/:systemType/calculate` | 出生信息类计算（八字/紫微/西方占星/印度占星），body 为 `BirthBasedInput` + `profileId` |
| POST | `/api/divination/:systemType/cast` | 起卦事件类计算（六爻/奇门/梅花/小六壬/塔罗/卢恩/占星骰/生命灵数/测字），body 为 `DivinationEventInput` |
| GET | `/api/divination/charts/:id` | 读取任意类型的命盘结果（按 `systemType` 分支反序列化 `chartJson`） |
| POST | `/api/divination/reports/:chartId/:dimension` | 生成 AI 解读（复用现有 `ReportsService` 的流式管线，`dimension` 集合随 `systemType` 变化，如塔罗只有 `overview` 一个维度） |
| POST | `/api/divination/ask/:chartId` | 命盘/卦象问答（完全复用现有 `askStream` 逻辑） |
| GET | `/api/content/:systemType` | 获取该系统的教程/案例解析列表 |

### 9.2 现有路由兼容性

现有的 `/api/charts/*`（八字专用）**保持不动**，作为 `systemType='bazi'` 的历史兼容路由长期保留，避免破坏现有前端调用与可能存在的第三方集成。新前端页面统一走 `/api/divination/*`，八字页面可选择迁移或保留双路由并存（建议保留，风险最低）。

### 9.3 统一响应结构（沿用现状）

```json
{ "code": 0, "message": "ok", "data": {} }
```

沿用 `common/dto/api-response.ts` 与 `http-exception.filter.ts` 现有机制，不新增规范。

## 十一、计费与额度体系扩展

### 11.1 现有机制回顾

`UserQuota` 表当前按"月度重置的 overview/report/ask 三类调用次数 + 累计 token/成本"计量，`plan` 只有 `free`/`pro` 两档，`pro` 不限量。

### 11.2 扩展方案：按"系统类型"精细化，而非简单复用

**关键决策**：新模块**不建议**简单复用现有的 `usedOverviewCalls`/`usedReportCalls` 字段全局计数，否则用户测一次塔罗就会占用八字报告的免费额度，体验割裂。改为按 `systemType` 维度记录用量：

```prisma
/// 改造 UserQuota：新增按系统类型的用量 JSON 字段（轻量方案，不新建关联表）
model UserQuota {
  // ...现有字段全部保留
  /// 新增：按系统类型的调用计数，结构如 { "tarot": {"used": 2, "free": 1}, "ziwei": {...} }
  /// 用 JSON 而非关联表，避免每新增一个系统都要写迁移
  systemUsageJson Json @default("{}") @map("system_usage_json")
}
```

### 11.3 免费额度策略建议

| 系统类别 | 免费额度策略 | 理由 |
|---|---|---|
| 出生信息类（八字/紫微/占星） | 每月 1 次免费"整体概览"（沿用现状） | 计算成本相同，模式统一 |
| 起卦事件类·高频轻量（塔罗/梅花/小六壬/卢恩/星骰） | 每日 1 次免费（而非每月），无限次起卦但解读受限 | 这类工具的用户价值在于"随手一测"的高频互动，月度限额会扼杀产品特性，日度限额更符合使用场景，且能提升 DAU |
| 数理类·极低成本（生命灵数） | 完全免费不限量 | 计算与解读成本极低（单条知识库文本，甚至可以不走 LLM 直接返回模板文案+少量 LLM 润色），作为免费引流工具而非付费点 |
| 六爻（问答式，成本较高） | 每月 3 次免费 | 六爻需要完整的用神分析，LLM 调用成本接近八字维度报告 |

### 11.4 Pro 套餐范围调整

现有"解锁完整版"含义需要重新定义：是"解锁全部术数系统的完整报告"还是"按系统单独解锁"？建议采用**分层订阅**：
- **基础 Pro**（现有定价）：解锁八字 + 紫微 + 六爻等"东方术数"模块的完整报告与问答。
- **全系 Pro**（新增更高档，或作为唯一档但提价）：解锁全部四大模块。

这是产品定价决策，不在本技术方案范围内展开，仅在此标注需要与盈利方案文档（`docs/盈利方案.md`）联动更新。

## 十二、合规与安全（新增风险点汇总）

在现有合规措施（免责声明、内容过滤、敏感字段加密、访问控制）基础上，新模块引入的**增量风险**：

| 风险点 | 涉及模块 | 应对措施 |
|---|---|---|
| 生物识别信息（人脸特征） | 面相/手相 | 用完即焚（不落库原图）；独立同意书；明确告知不做身份核验用途 |
| 用户上传图片的一般隐私风险 | 面相/手相、笔迹学 | 同样建议不持久化原图，仅保留 AI 提取的文字特征描述 |
| 伪科学争议内容的表述边界 | 笔迹学、通灵板/扶乩 | 笔迹学需加强"娱乐参考"措辞；通灵板/扶乩类**不纳入产品范围**（已在第 6.5 节说明） |
| 流派权威性争议 | 紫微斗数、奇门遁甲、果老星宗 | 文档与前端页面注明"本系统采用 XX 流派通行排法，不同流派可能得出不同结论" |
| 天文计算精度对外部库的依赖 | 西方占星、印度占星 | Swiss Ephemeris 的授权协议需确认（其历史上有 GPL / 商业双授权模式，需在选型阶段核实当前授权条款是否符合商用要求） |
| 起卦类输入的"随机数"公正性质疑 | 塔罗、六爻、梅花、卢恩、占星骰 | 使用加密安全随机数（`crypto.randomInt`），前端展示"起卦时间戳"增加可信度，避免被质疑"结果可操控" |
| 跨模块的内容审核工作量陡增 | 全部新模块 | RAG 知识库内容量级从当前的约 80 条扩张到未来上千条，需要建立内容审核 SOP（而非现有的"开发者手写即上线"模式），建议在 M2 阶段引入知识库内容的双人审校流程 |

### 12.1 免责声明的模块化改造

现有 `Disclaimer.tsx` 是单一静态文案，建议改为按 `systemType` 传参渲染差异化措辞（例如面相模块需追加"不用于医美/整形建议"，笔迹学需追加"心理学界对笔迹分析科学性存在争议，本功能仅供娱乐"）。

## 十四、总结：给你的下一步行动建议

1. **先做架构升级（第二章），不要先做具体模块**。哪怕只是把 `Chart.systemType` 字段加上、`DivinationEngine` 接口定义出来，后续每个模块的开发都会顺畅得多，这是本方案区别于"逐个模块单独开发"的核心价值。
2. **M1 阶段选生命灵数 + 塔罗作为架构验证田**，原因很直接：生命灵数几乎零算法风险用来验证"流程通不通"，塔罗验证"内容量大的知识库怎么管理、怎么审校"，这两个问题在后续所有模块里都会重复遇到，越早暴露越好。
3. **西方占星单独放一个阶段（M4）**，因为 Swiss Ephemeris 的技术选型是本方案唯一的"卡脖子"风险点，建议在正式排期前先花 1-2 天做技术尖刀验证（spike），确认能在你的部署环境（Docker + Node）里跑起来，再决定是否按此排期。
4. **面相手相、笔迹学等图像类模块，先确认合规方案再排期**，这两个模块的工程实现不难，难点在于"用完即焚"的存储策略设计和用户同意流程，建议提前与产品/法务角度过一遍再进入开发。
5. **奇门遁甲、大六壬、铁板神数、通灵板类内容，不建议在近期（M1-M4）投入**，前三者复杂度和准确性风险过高，后者合规风险过高，可以在功能导航里保留"即将上线"占位吸引关注度，但不投入工程资源。

如果你需要，我可以下一步直接开始 M1 阶段的编码工作：先搭 `DivinationEngine` 统一接口和 `Chart.systemType` 迁移，然后实现生命灵数引擎（工作量最小，最适合先跑通整条链路）。
