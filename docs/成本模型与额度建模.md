# 阶段 0：成本模型与额度建模

> 目标：先知道「每个用户每月花多少钱」，为定价提供依据，并据此设计用户级额度限制。

## 一、成本构成总览

| 环节 | 是否调用 LLM | 成本 | 说明 |
|------|:---:|------|------|
| 排盘计算（本地 bazi-engine） | 否 | ≈0 | 免费引流，不产生成本 |
| 单维度报告（stream / generate） | 是 | 有 | 唯一真正成本 |
| 整体概览（overview） | 是 | 有 | 同上 |
| 命盘问答（ask，含历史） | 是 | 有 | 随对话历史线性增长 |

- 排盘引擎本地计算、Redis 缓存、Postgres 落库均不计入 LLM 成本。
- LLM 成本只来自 `reports` 模块的三类接口：`stream`（单维度）、`overview`（概览）、`ask`（问答）。

## 二、单次 LLM 调用的 token 构成

> 依据 `prompt.builder.ts` 的构建逻辑。

### 输入 token（prompt_tokens）

| 组成 | 来源 | 估算量 |
|------|------|------|
| 系统约束 | `SYSTEM_CONSTRAINTS` | ~300 字 |
| 排盘事实块 | `formatChartFacts` | 400-600 字 |
| 知识参考块 | `formatKnowledge`（RAG 召回 4-6 条） | 300-600 字 |
| 维度指令 + 输出结构 | `STRUCTURED_OUTPUT_GUIDE` 等 | 100-200 字 |
| 问答：历史对话 | `buildAskMessages` 的 history | 随轮次增长 |

> 所谓「字」按 `estimateTokens` 估算：1 字 ≈ 1.5 token。

### 输出 token（completion_tokens）

| 组成 | 说明 |
|------|------|
| 正文 | 单维度报告约 700 token；概览约 1000-1200 token |
| 推理思考（reasoning） | **DeepSeek-V4-Flash 推理模型消耗 1000-1700 token**，已计入 completion |

## 三、计算逻辑

```
单次成本(CNY) = (输入token / 1e6 × 输入单价) + (输出token / 1e6 × 输出单价)
输入成本 = 命中缓存token × 缓存单价 + 未命中token × 标准单价
```

单价表（`pricing.ts`，**人民币** / 每百万 token，来自 DeepSeek 官方定价页 https://api-docs.deepseek.com/zh-cn/quick_start/pricing ）：

| 模型 | 输入(未命中) | 输入(缓存命中) | 输出 |
|------|:---:|:---:|:---:|
| deepseek-v4-flash | ¥1 | ¥0.02 | ¥2 |
| deepseek-v4-pro | ¥3 | ¥0.025 | ¥6 |
| deepseek-reasoner | ¥1 | ¥0.02 | ¥2 |
| deepseek-chat | ¥1 | ¥0.02 | ¥2 |
| gpt-4o-mini | ¥1.08 | — | ¥4.32 |
| gpt-4o | ¥18 | — | ¥72 |
| 兜底 * | ¥1 | ¥0.02 | ¥2 |

> 兼容旧模型名：`deepseek-chat`/`deepseek-reasoner` 已于 2026/07/24 弃用，分别对应 v4-flash 的非思考/思考模式，价格同 flash。gpt 价格为美元按 7.2 汇率折算，仅供参考。

### Token 换算（官方口径）

DeepSeek 官方（https://api-docs.deepseek.com/zh-cn/quick_start/token_usage ）：
- 1 个中文字符 ≈ 0.6 token
- 1 个英文字符/数字/符号 ≈ 0.3 token

`estimateTokens` 已按此实现（离线估算，实际以模型返回的 usage 为准）。

### 真实成本估算（DeepSeek-V4-Flash，含 reasoning 计入输出）

| 场景 | 输入 token | 输出 token | 估算成本 |
|------|:---:|:---:|------|
| 单维度报告 | ~1350 | ~1975 | ~¥0.0039 |
| 整体概览 | ~1530 | ~2350 | ~¥0.0052 |
| 一次问答（无历史） | ~1350 | ~1900 | ~¥0.0038 |
| 一次问答（含 5 轮历史） | ~3350 | ~1900 | ~¥0.0047 |
| 完整套餐（7 维度 + 概览） | ~10980 | ~16175 | ~¥0.031 |

> 实时接口：`GET /api/reports/cost-per-package`（需登录）返回以上明细，含各维度、概览、问答（首轮/含历史）以及套餐总成本的 token 与人民币成本，并附 `pricing`（含缓存价）与 `assumptions`。
> 计算示例（单维度报告，deepseek-v4-flash 价，缓存未命中）：
> `(1350/1e6)×1 + (1975/1e6)×2 = 0.00135 + 0.00395 ≈ ¥0.0053`（实际接口按 estimateTokens 精确计算）

### 关键结论

- **单次成本极低**（约 ¥0.004-0.005），成本不是单次问题。
- 命中 prompt 缓存后输入成本可低至 ¥0.02 / 百万 token，鼓励复用相同系统提示词。
- 真正的成本威胁是 **用户量 × 使用次数** 的累积。
- 定价必须覆盖「免费用户产生的一次概览 + 付费用户多次使用」，并设额度上限防滥用。

## 四、用户级额度建模（UserQuota）

### 设计目标

1. 按用户计量每月的 LLM 消耗（token 总量 + 成本）。
2. 用「免费额度」限制免费用户，防滥用；付费用户解锁。
3. 让成本看板能「按单用户」统计，而非只按单次报告。

### 数据模型（Prisma）

在 `User` 增加关联，新增 `UserQuota` 表：

```prisma
model User {
  // ...现有字段
  quota  UserQuota?
}

/// 用户额度与消耗（按月计量）
model UserQuota {
  id               String   @id @default(uuid())
  userId           String   @unique @map("user_id")
  plan             String   @default("free") // free | pro
  /// 免费额度每月重置
  freeReportCalls  Int      @default(1)   // 免费次概览/报告次数
  freeAskCalls     Int      @default(3)   // 免费次问答
  usedReportCalls  Int      @default(0)
  usedAskCalls     Int      @default(0)
  /// 累计消耗（不重置，用于成本核算；单位：人民币）
  lifetimeTokens   BigInt   @default(0)
  lifetimeCost     Decimal  @default(0)
  monthKey         String   @default("")  // 如 "2026-08"，用于识别重置周期
  updatedAt        DateTime @updatedAt
  user             User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  @@map("user_quotas")
}
```

### 计量埋点

- 在 `reports.service` 的 `generateDimension` / `generateOverviewStream` / `askStream` 调用结束后，把 `usage`（或估算值）累加进 `UserQuota`。
- 流式场景拿不到 usage，用 `estimateTokens` 按输出长度估算，保证成本统计不缺失。

### 额度校验拦截

- 在 `reports.controller` 每个接口前加额度校验：免费用户超限返回 402「额度不足，请升级」。
- 付费（pro）用户不设上限。

### 成本看板扩展

- 现有 `costStats` 补齐「按用户排行」：`topUsers` 返回消耗最多的 N 个用户及其 token/成本。
- 新增 `UserQuota` 后，看板可展示「本月免费用户消耗 vs 付费用户消耗」。

## 五、落地顺序建议

1. 先建 `UserQuota` 表 + 迁移。
2. 在 `reports.service` 加计量埋点与额度校验。
3. 扩展 `costStats` 看板支持按用户统计。
4. 根据真实数据校准 `pricing.ts` 的单价与免费额度数值。
